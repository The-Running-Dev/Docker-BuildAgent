## F1

Severity: BLOCKING
Status: defect — sustained, 2026-09-19. Resolved by re-keying the lock on the target container's name; see `design/90-decisions.md` → *2026-09-19 — Update lock is keyed on the container name, not the container id* and `design/10-design.md` § *Update lock*.
Claim: The update mutex changes identity while the update still owns it, so a second update of the same named container can acquire a different lock.
Where: `design/10-design.md` § *Update lock*, § *Control flow* → *An operator updates a named container*, and § *Concurrency and ordering* → *Container updates*
Breaks when: Update A locks original container id `O`, renames that container, creates replacement id `N` under the original name, and waits for health; update B then resolves the same name to `N` and derives a lock name from `N`, which does not conflict with A's lock derived from `O`.
Consequence: Both updates can mutate the same logical container concurrently despite the brief's required same-container refusal; either update can remove, rename, or restore state the other still assumes it owns.
Cost: Expensive to fix later — lock identity is coupled to update records, residue detection, restore semantics, cleanup, and concurrency tests, and a field failure can leave container state that neither update can interpret safely.

## F2

Severity: BLOCKING
Status: defect — sustained, 2026-09-19. Resolved by moving the pull outside the lock and deleting automatic takeover; see `design/90-decisions.md` → *2026-09-19 — A stale update lock is reported, never taken over, and the pull moves outside it* and `design/10-design.md` § *Update lock*.
Claim: Stale-lock takeover is not mutually exclusive with the original owner because the design has neither a bounded critical section nor a way to stop an owner whose lock was removed.
Where: `design/10-design.md` § *Update lock*, § *Control flow* → *An operator updates a named container*, and § *Concurrency and ordering* → *Container updates*
Breaks when: A pull or Docker operation lasts past `health timeout + fixed margin`, or the taker's clock is sufficiently ahead of the owner's; the taker removes the lock by id and recreates it while the original process is still running and continues past its next step.
Consequence: Two owners execute the supposedly sequential stop, rename, create, health, and restore sequence. Removing the old lock by id protects a newly created lock from deletion, but it does not prevent the old owner from continuing to mutate the target.
Cost: Expensive to fix later — the failure is timing-dependent, crosses process and machine boundaries, and can invalidate every recovery assumption after users already rely on unattended rollback.

## F3

Severity: BLOCKING
Status: unadjudicated
Claim: The release gate allows mechanically visible protected-surface changes that the brief classifies as breaking.
Where: `design/00-brief.md` § *Compatibility promise*; `design/10-design.md` § *Surface manifest* and § *Control flow* → *A maintainer releases a version*
Breaks when: A minor release changes a recorded parameter type, changes the image entrypoint, or reorders Docker-template discovery locations without removing or renaming an item or changing a recorded default; the manifest contains the changed data, but the comparison rules test only removal, rename, changed default, and removal without prior deprecation.
Consequence: The pipeline can publish a minor version that changes documented behaviour or selects a different Dockerfile, breaking pinned consumers while every designed release gate passes.
Cost: Expensive to fix later — once such a minor release is immutable and public, the compatibility promise cannot be restored without another migration and consumers cannot infer safety from the version number.

## F4

Severity: BLOCKING
Status: unadjudicated
Claim: A release claim contains no evidence that an existing sink artifact was produced by that claim, yet resume safety depends on proving exactly that relationship.
Where: `design/10-design.md` § *Release claim* and § *Failure modes* → *Partial publish*
Breaks when: A retry finds version `2.0.0` in a registry or package feed while a same-SHA draft claim exists; the claim records the version, commit, state, notes, and surface manifest, but no per-sink artifact identity, digest, receipt, or completion state distinguishes the intended artifact from an orphaned or externally published artifact with that version.
Consequence: The retry can assemble one release from artifacts that do not share the claimed commit, or it can refuse a legitimate resume because it cannot establish that an existing artifact is "under this claim." Published package versions and image tags then disagree while presenting one shared product version.
Cost: Expensive to fix later — immutable packages cannot be replaced cleanly, so the first ambiguous partial publication can permanently consume the version and strand the release.

## F5

Severity: BLOCKING
Status: unadjudicated
Claim: The draft claim is described as a concurrency backstop even though claim checking and claim creation are non-atomic and the design explicitly permits two drafts in that window.
Where: `design/10-design.md` § *Release claim* and § *Concurrency and ordering* → *Releases* and *Claim race*
Breaks when: Two publishing runs for the same version but different commits bypass or misconfigure the shared CI concurrency group, both finish the absence check, and both create drafts before either observes the other.
Consequence: Both runs can reach mutable image publication, while package feeds reject whichever arrives second; the same version can temporarily or permanently identify different commits across sinks, and the versioned image tag can be overwritten despite the immutability promise.
Cost: Expensive to fix later — the race is rare enough to evade ordinary testing but consumes immutable public versions and leaves a cross-sink state that retries cannot safely reconcile.

## F6

Severity: STRUCTURAL
Status: unadjudicated
Claim: The global tool is both a launcher that shares no code with Build types and the host of an updater that depends on a notification service declared to live within Build types.
Where: `design/10-design.md` § *Module boundaries*, including the Launchers and Updater rows and the dependency rules below the diagram
Breaks when: The global tool is packaged: satisfying the updater dependency requires the host package to reference Build types or a service owned inside it, while the launcher boundary requires the package to treat the image as a black box and share no Build types code.
Consequence: The implementation must violate one stated boundary or duplicate the service. Changes to build-internal notification code can ripple into the host tool and its Linux/Windows support surface.
Cost: Expensive to fix later — once package references and shared types cross this boundary, separating them affects the image build, host tool, notifications, tests, and release packaging together.

## F7

Severity: STRUCTURAL
Status: defect — sustained, 2026-09-19. Resolved by refusing, before any change, a target whose replacement cannot be created faithfully; see `design/90-decisions.md` → *2026-09-19 — An update refuses a container whose replacement cannot be created faithfully* and `design/10-design.md` § *Control flow* step 2.
Claim: The update path creates the replacement from inspected configuration using the same source the design rejects as too lossy for faithful container recreation.
Where: `design/10-design.md` § *Control flow* → *An operator updates a named container* step 8 and § *Alternatives considered* → *Preserving and restoring the prior version*
Breaks when: The target uses an anonymous volume, link, or runtime option that inspect output cannot reproduce faithfully; the updated container is created from that inspected configuration, passes its internal health check, and the original container is then removed as a successful update.
Consequence: A successful update can silently change storage, connectivity, or runtime behaviour, and after success the exact original container that could restore those settings has been deleted.
Cost: Expensive to fix later — supported configuration preservation determines refusal rules, update semantics, health coverage, and what rollback can promise across Docker versions and both supported host platforms.
